현업 스타일 브랜치 전략부터 PR, 머지 권한 제한, 충돌 해결까지 — git switch 기준

Git Bash 터미널에서 명령어로 실행 웹 GitHub 사이트에서 클릭으로 실행 개념 헷갈리기 쉬운 개념 정리
1저장소 구조 만들기웹

팀장 1명이 저장소를 생성하고, 나머지 팀원 2명을 Collaborator로 초대합니다.

  • Settings → Collaborators → Add people 로 팀원 초대
  • 초대받은 팀원은 이메일/알림에서 Accept를 눌러야 push 권한이 생김
  • 저장소는 Public으로 생성 (main 보호 규칙이 Private에서는 무료로 작동하지 않음 — 7번 카드 참고)

초대 수락 후, 팀원 각자 Git Bash에서 저장소를 내려받습니다.

git clone https://github.com/팀장아이디/team1-bigdata-project.git
cd team1-bigdata-project
2브랜치 전략Git Bash

3명 규모에는 main + 기능별 브랜치면 충분합니다. Git Flow의 dev 브랜치는 도입하지 않습니다 (이유는 9번 카드).

main — 항상 살아있는 코드, 최종 제출용
feature/1-data-collection — 데이터 수집 (Issue #1)
feature/2-eda-report — EDA 리포트 (Issue #2)
fix/3-streamlit-filter — 대시보드 필터 수정 (Issue #3)

브랜치 이름에 이슈 번호를 넣습니다. 어떤 이슈에서 나온 작업인지 이름만 봐도 연결됩니다.

# main 기준으로 새 브랜치 생성 + 이동
git switch main
git switch -c feature/1-data-collection

# 원격 저장소에도 등록
git push -u origin feature/1-data-collection
브랜치를 feature라고만 짓지 않도록 주의하세요. 실제로 -c feature까지만 치고 슬래시 뒤를 빠뜨리는 실수가 잦습니다. 잘못 만들었다면 git branch -m feature feature/1-data-collection로 이름을 고칠 수 있습니다.
3작업 시작 전 루틴 (매일 반복)Git Bash

가장 많이 헤매는 지점입니다 — 내 브랜치가 팀원 작업을 반영 못 해서 나중에 충돌이 크게 터집니다.

# 1. 작업 시작 전, 항상 main 최신화
git switch main
git pull --ff-only origin main

# 2. 내 feature 브랜치로 이동 후 main 내용 병합
git switch feature/1-data-collection
git merge main

# 3. 작업 → add → commit
git add .
git commit -m "#1 OpenAPI 수집 함수 추가"

# 4. 원격에 내 브랜치 push
git push origin feature/1-data-collection
--ff-only는 안전장치입니다. 히스토리가 일직선으로 이어질 수 있을 때만 pull이 성공하고, 안 되면 원인 모를 머지 커밋 대신 에러를 내고 멈춥니다. 학생이 "뭔가 꼬였다"를 바로 알아챌 수 있게 해줍니다.
4Pull Request 요청하기웹

Git Bash에서 push까지 하면, 그다음부터는 GitHub 웹사이트에서 진행합니다. 상황에 따라 두 가지 방법이 있습니다.

방법 A — 방금 push한 직후

push하면 저장소 화면 상단에 노란 배너로 Compare & pull request 버튼이 바로 뜹니다. 클릭하면 됩니다.

방법 B — 이미 push된 브랜치로 나중에 열 때

브랜치 화면(.../tree/브랜치명)에 들어가면 "This branch is N commit ahead of main" 안내와 함께 Contribute 드롭다운이 보입니다. 클릭 → Open pull request.

Open 2번째 데이터 파일 추가 (#4)
팀원이 feature/1-data-collection → main 병합을 요청함 · Reviewer: 팀장
  • Title / 설명 작성
  • Reviewers에 팀장 지정
  • 이슈와 연결하려면 설명란에 closes #1 작성 (머지되는 순간 이슈 자동으로 닫힘)
  • Create pull request 클릭 → 여기까지가 팀원의 역할
5PR 요청과 Merge는 다릅니다개념

여기서 제일 많이 헷갈립니다. "PR을 연다"와 "Merge 한다"는 완전히 다른 동작입니다.

PR 요청 (열기)Merge (병합)
하는 일"내 코드를 main에 반영해주세요" 요청만 함실제로 main 코드를 바꾸는 행위
누가 할 수 있나Collaborator면 누구나제한 가능 (7번 카드 설정)
버튼"Create pull request"PR 안의 "Merge pull request"

즉 팀원은 PR을 자유롭게 열 수 있지만(요청), 그 PR의 Merge 버튼을 누르는 것(실행)은 다음 카드 설정으로 팀장만 가능하게 제한할 수 있습니다.

참고로 PR에 그냥 댓글(Comment)만 다는 것은 승인(Approve)과 다릅니다. "Required approvals" 조건은 초록색 Approve 버튼을 누른 사람 수만 세고, 일반 댓글은 카운트되지 않습니다.

6충돌(Conflict) 해결Git Bash

설명만으로는 안 와닿습니다. 3명이 같은 파일의 같은 줄을 각자 수정 후 순서대로 merge 시켜 의도적으로 실습시키세요.

git merge main
CONFLICT (content): Merge conflict in README.md
<<<<<<< HEAD
내가 작성한 내용
=======
main에 있던 내용
>>>>>>> main

VS Code에서는 "Accept Current / Accept Incoming / Accept Both" 버튼으로 더 직관적으로 해결 가능합니다.

# 해결 후
git add README.md
git commit -m "resolve conflict"
git push origin feature/브랜치명
7main 보호 설정 — 팀장만 Merge 가능하게웹
사전 조건: 저장소가 반드시 Public이어야 합니다. Rulesets는 Private 저장소에서 유료(GitHub Team, $4/user/월) 전환 없이는 작동하지 않습니다. Private을 유지해야 한다면 카드 맨 아래 대안을 참고하세요.

경로: 저장소 → Settings → Rules → Rulesets → New branch ruleset

① 기본 정보

Ruleset Name아무 이름 (예: main-protection)
Enforcement statusActive
Target branchesDefault 그대로 두면 됨 (= main과 동일)

② Bypass list — 팀장만 예외 처리 (여기가 핵심)

Add bypass → Repository admin (Role) 체크. 팀장은 저장소 소유자라 자동으로 Repository admin입니다.

③ Branch rules 체크리스트

☑ Restrict updates              # 팀원 merge 차단의 핵심
☑ Restrict deletions            # main 삭제 방지
☑ Require a pull request before merging
     Required approvals: 1      # 반드시 0이 아닌 1 이상
☑ Block force pushes            # 강제 push로 우회 방지

Allowed merge methods는 Squash 추천 — 팀원이 커밋을 여러 번 남겨도 main에는 PR당 한 줄로 깔끔하게 들어갑니다.

맨 아래 Create 클릭하면 완료됩니다.

행동팀원팀장
브랜치 생성 / commit / push✅✅
PR 열기 (요청)✅✅
PR 리뷰 / 코멘트✅✅
Merge 버튼 클릭❌ 막힘✅

테스트 방법: 팀원 계정으로 PR을 열고 Approve까지 받은 뒤 Merge 버튼을 눌러보게 하세요. 비활성화되거나 권한 오류가 뜨면 정상입니다. 팀장 계정으로 같은 PR에서 Merge가 되는지 마지막으로 확인하세요.

Private을 꼭 유지해야 한다면: Settings → Branches → Add branch protection rule(예전 방식, 무료)로 "Require a pull request before merging" + "Required approvals: 1"까지는 강제할 수 있습니다. 다만 "팀장만 bypass" 기능은 없어서, "팀장 승인 전엔 Merge 버튼 누르지 않기"를 운영 규칙으로 함께 공지해야 합니다.
8협업 최소 규칙
  • main에 직접 push 금지 (Rulesets로 강제)
  • 하루 작업 끝나면 반드시 push
  • 커밋 메시지: #이슈번호 한줄설명 형태로 통일
  • 작업 전 git pull --ff-only, 작업 후 git push — 습관화
  • Merge는 팀장만 — 팀원은 PR 요청까지
9브랜치 네이밍 컨벤션

feature는 "기능"이라는 뜻입니다. 접두사를 목적별로 다르게 붙이면 브랜치 이름만 보고 무슨 작업인지 바로 알 수 있습니다.

접두사의미예시

지금 팀 프로젝트는 전부 새 기능이라 feature/만으로 충분합니다.

10이슈 만들기 & 브랜치 연결웹

Issue는 git 명령어가 아니라 GitHub 자체 기능입니다. Git Bash로는 만들 수 없고, 웹에서만 가능합니다.

  • Issues 탭 → New issue → Title 입력 → Assignees에 담당자 지정 → Create
  • 번호는 직접 입력하는 게 아니라 저장소별로 자동 증가 (첫 이슈는 #1)
  • 이슈 생성은 팀장뿐 아니라 Collaborator 누구나 가능 — 본인 작업은 본인이 이슈부터 만드는 걸 추천

이슈 상세 페이지 → Development → Create a branch로 바로 연결된 브랜치를 만들 수도 있습니다 (선택). 이름을 feature/1-... 형태로 직접 고쳐도 이슈 연결은 그대로 유지됩니다.

# Create a branch가 만들어준 브랜치를 로컬로 받기
git fetch origin
git switch feature/1-data-collection

git add .

### 4. (웹) PR 열기 → 리뷰 → Approve → Merge는 팀장만
